SENTINEX Build Documentation · Process Reference
Ways of Working — Constitution & Execution Flow
The invariants we hold (constitution), the rhythm we run each session on top of them, and the delta when that session runs from mobile: sync → orient → spec → build → demo → sign-off → hand off
Distilled from .claude/rules (harness · build · product) Living — update when the working agreement changes
What this is. A single map of the working agreement encoded across .claude/rules/harness.md, build.md and product.md plus build/PROGRESS.md. Three parts: the Constitution (the invariants every session inherits — design doctrine, engineering practices, and the harness automation that enforces them), the Execution Flow (the six-phase rhythm run on top of them), and the Mobile Execution Delta (what additionally changes when that rhythm runs from a mobile/cloud session with no physical machine). In the flow, amber = a gate that must be cleared before continuing; red = a hard guardrail that has bitten us before. One phase of the MVP is executed per session; the loop closes by arming the next session.
Part A · Constitution — the invariants every session inherits
Pillar I
Design Principles
🔒Sovereign by construction. On-premise, air-gapped in production. Data sovereignty is the core selling point, not a feature.
🧩Open-source only. Open-source components & LLMs; no cloud APIs, no closed models, no telemetry callouts in pipeline code.
✂️Deliberate simplicity. Single-broker Kafka, Postgres FTS (no Elasticsearch), server-rendered dashboard first — earn each moving part.
📜Schemas are the contract. schemas.py is the pipeline contract; bump schema_version on breaking changes, never mutate silently.
🏷️Fixed vocabulary. The five module names are canonical and used verbatim everywhere.
🛡️Sensitivity firewall. Programme/customer names never touch repo-surface (README, commits, tags, CI, code); neutral phrasing there.
Pillar II
Engineering Practices
📝Spec-first. Every phase spec — objective, scope, components, exit checks, NFR targets — is written before a line of implementation.
🌳Trunk-based on CI-gated main. GitHub Actions (ci.yml) runs the network-free unit suite on every push; annotated tag per phase at sign-off.
📐NFR-driven. Explicit targets measured, not asserted; standing bar <200 ms/item P95; index per query predicate; bounded drop-oldest backpressure.
🔁Verify against the live stack. Idempotent, re-runnable test scripts; restart/replay = 0 loss / 0 duplication.
📊MEASURED vs PROJECTED, never blurred. Dev-scale and production-scale ladders kept separate in every claim.
📚Living documentation. AsBuilt diagrams, PROGRESS.md decisions log, and REQUIREMENTS_TRACE.md kept current as the code moves.
📦Reproducible environment. Pinned venv (Python 3.14) + docker-compose stack; native-service fallback when the machine is away.
🚫What efficiency never cuts. Spec-before-implementation, the unit suite, live verification against real data, logged reviews with resolutions, and the PROGRESS.md / user-guide rituals stay whatever the token budget says. Edit/Write results average 544 chars — verification discipline is not what costs money. Cut the cost of looking, not the looking itself.
🧪Optional deps never break collection. CI installs [dev] only — a test needing [nlp]/[cv] uses pytest.importorskip, and optional model imports live inside functions. A bare top-level import fails at collection and takes the whole suite with it. Check gh run list after any push that adds a test module or a dependency.
Pillar III
Harness Rules & Automation
🪝Harness hooks — three, all report-only. Wired in settings.json. At session start: git_sync_check.sh prints origin divergence; serving_check.sh prints whether the server on :8000 is serving HEAD. Before every Read: token_check.sh warns when the read is an image (T2), a path already read this session (T7/T8/T9), or a >400-line file being read whole with no offset/limit (T7). None of the three mutates, kills or blocks anything — acting on the output is the rule, not the hook. Each is exercised by its own test suite, because a hook's failure mode is silence and nobody notices silence.
⚖️Why every hook warns and none of them blocks. A rules file cannot interrupt — it loads as passive context and is followed, or is not. That is why prose alone failed twice: the git-sync rule "already existed as prose above and was skipped anyway", and tokens.md had the same shape. So a rule that must not be skippable becomes a hook. But the hook warns: it never auto-merges a dirty tree, never kills a server, never denies a read. Each of those has a legitimate case (T3 covers images that genuinely belong in the main context), and a hook that blocked one would be a worse trap than the problem it guards.
📖Loaded rulebook. CLAUDE.md + .claude/rules/{harness,build,product,tokens}.md load every session as binding instructions.
💰Token efficiency is a way of working, not a footnote. tokens.md (2026-08-03) is derived from a full measurement of this project's own 41 transcripts — 26 days, USD 682.10. The mechanism it turns on: a tool result is re-read on every subsequent turn, so cost ≈ size × turns remaining — MEASURED amplification mean 133×, peak 364×. Screenshots read into the main context were 22% of all spend from 63 calls; subagent usage was zero, the largest unused lever. Practice: structural check before screenshot, screenshot read in a subagent, grep-then-offset reads, session-start files read once, end sessions at phase boundaries. Re-measured at each MVP boundary, same cadence as the AsBuilt refresh.
⚙️Permission policy. settings.json allow/deny/ask lists scope what runs without a prompt; settings-edit caveat respected.
🧰Project skills. write-prd, define-metrics, sentinel-stack, update-config — used instead of ad-hoc structure.
🤖Project subagents. sentinel-code-reviewer (runs before any push touching src/tests/infra, and writes its review to a file before returning), sentinel-spec-drafter, and sentinel-sme. Also the standing delegation pattern: large payload, small answer — visual verification, repo-wide search, reading a long log to answer one question. The subagent's context dies at return, so the payload never amortises against the session. Delegate breadth, never judgement that needs the main thread's accumulated context.
🧠Persistent memory. File-based memory with a MEMORY.md index carries decisions across sessions.
🚧Standing gates. Token-budget gate, multi-device sync gate, and session-branch discipline are enforced before / around the flow. The budget gate decides whether a step fits; tokens.md governs how the approved budget is spent — the two are answered together.

Part B · Execution Flow — the rhythm we run each session

1 Sync & Orient first tool call of every session · harness.md
1.1 · SESSIONSTART
Fetch before reading anything
git fetch origin main + rev-list --left-right --count HEAD...origin/main. The multi-device sync gate — a local clone goes stale silently.
→
1.2 · DECISION
Behind origin/main?
Yes → status --porcelain, diff for collisions, pull --ff-only, then re-read PROGRESS.md. If pyproject.toml moved, reinstall the venv. No → continue.
→
1.3 · READ
PROGRESS.md, then the master spec
Read build/PROGRESS.md (post-fetch), then the pinned MVP<N>_..._MASTER_SPEC.md. Never re-read proposal PDFs for scope.
Guardrail — never answer status from an unfetched tree. "Where are we / what's the latest" feels read-only and is exactly the prompt that once reported the MVP two phases behind reality. State which commit a status was read at.
↓
2 Scope & Gate agree the increment before spending tokens
2.1 · ALIGN
Ask clarifying questions
Confirm the one phase for this session, its boundaries, and any open decisions — before writing anything.
→
2.2 · TOKEN-BUDGET GATE
Fits the quota?
For any costly step (>~100k tokens): ask Nitish's 5-hour % and weekly %, estimate cost against both, state whether it fits, and proceed only on his go. Then name which tokens.md rules bring the estimate down — "it fits" is a weaker answer than "it fits, and T2 keeps the screenshots out of the main context".
→
2.3 · SESSION-SPLIT GATE
Scope only, or scope + build?
Budget fitting is necessary but not sufficient — a second, independent call driven by the phase's risk shape, not its token cost.
→
2.4 · CONSTRAINTS
Load the invariants
Air-gapped / open-source-only / no cloud APIs. schemas.py is the pipeline contract. Repo-surface = neutral phrasing, no programme/customer names.
POC-shaped / self-contained (extends existing data/plumbing, no new model, no unresolved external dependency — W1's map, W2's AIS+geofence, W3's CII) → default to scope + build in one pass when budget allows; splitting mostly re-derives context for no real risk-reduction. Eval/risk-heavy (a new ML model to validate, an unresolved licensing/reachability question, an eval floor that must be measured before anything downstream can be designed against it — W5's deepfake detection, gated on OQ-W3) → scope only, resolve the open risk, stop for Nitish's review before committing to a build plan, even with ample budget. Decided 2026-07-25 (W3); name which path a session is taking and why, same as the budget-gate line above.
↓
3 Spec First written BEFORE implementation · build.md
3.1 · WRITE
Phase spec under the MVP folder
PHASE_<L><n>_SPEC.md (S/G/W/O prefix). Objective, in/out of scope, components to build, exit checks.
→
3.2 · DECLARE
Explicit NFR targets
Throughput, latency P50/P95/max (<200 ms/item P95), scale ceiling, resilience, storage, index coverage, backpressure — each a number to be measured, not asserted.
→
3.3 · TRACE
Keep scope consistent
Nothing contradicts the annexures or master spec. If scope tightens/extends, say so and update REQUIREMENTS_TRACE.md.
↓
4 Build & Verify a working, measured increment
4.1 · IMPLEMENT
Build the increment
Open-source components only; bump schema_version on breaking changes, never mutate silently. Engineering register in code/docs.
→
4.2 · TEST E2E
Exercise it against the live stack
Extend smoke_test.py or add a phase script — idempotent, re-runnable. Restart/replay = 0 loss / 0 duplication.
→
4.3 · MEASURE NFRs
Live, not asserted
Each target MEASURED against the stack at a stated scale. Tag every number MEASURED or PROJECTED — never blur dev and production.
→
4.4 · REVIEW TO FILE
Log the code review and its resolutions
sentinel-code-reviewer writes its own file under build/docs/reviews/ — CODE_REVIEW_<date>_<time>_<slug>.md — before returning; the session then fills in a Resolution per finding: fixed / deliberately not taken with the reasoning / deferred. A review living only in a subagent's return value is gone at the next compaction, and what is lost is which findings were deliberately not taken, and why.
if Nitish is away → don't default to "blocked, need Docker". Check the check's real footprint; Postgres/Redis + pure-Python API run natively in-container (Playwright screenshot as evidence). Hand-seeded fixtures are labelled as such. Kafka/MinIO or a policy-denied host is a genuine wall — record it as pending on a networked machine.
↓
5 Demo & Sign-off real data Nitish can see · then explicit approval
5.1 · RUNBOOK
Add the phase's journeys
Extend build/docs/DEMO_RUNBOOK.md with this phase's demo steps before the demo runs.
→
5.2 · SERVING GATE
Is the running server actually HEAD?
Before any demo, screenshot or sign-off: scripts/serving_check.py — 0 current / 1 stale / 2 listening but unreadable. It compares the served SHA to HEAD and catches what a SHA cannot: a same-commit process started before an uncommitted edit.
→
5.3 · DEMO + EVIDENCE
Run it live, capture proof
Demonstrate with real data he can see — query output, topic messages, browser UI. Capture screenshots / outputs and record them in the demo file. Every screenshot offered as evidence must carry the footer stamp build <sha> · started <time> · pid <n> legibly — that is what makes the evidence self-dating.
→
5.4 · SIGN-OFF GATE
Nitish explicitly approves?
Until approval → record as "built, awaiting sign-off". Approved → mark the phase COMPLETE. No self-sign-off.
Guardrail — the stale server that looks entirely current. A run api left listening on :8000 overnight served pre-T2-4 code all the next morning. Windows gives the first listener exclusive port ownership, so a second run api would have failed loudly — but nobody ever runs one: the dashboard is simply already open and healthy. Every verification surface the project had (healthz, the browser, a Playwright screenshot) was blind to which code it was verifying. A server that reports no build block at all predates 2026-07-28 and is stale by definition — restart it, do not reason about it.
↓
6 Close Out & Hand Off land on main · arm the next session
6.1 · MVP-BOUNDARY ONLY
Refresh the AsBuilt diagrams?
At MVP sign-off → update the seven living SENTINEX_*_AsBuilt.html (Architecture, CDM, Taxonomy, LDM, DFD, UseCase + the Business Walkthrough) in place — six refreshed structurally, the Walkthrough given a full narrative rewrite. Phase-level → skip. Edit in place; git history is the record, there is no versioned file per MVP for these seven.
→
6.2 · USER GUIDE
Sync that phase's own MVP guide
Any phase changing user-facing behaviour updates docs/user_guide/MVP<N>_<Name>.md — that phase's own MVP — in the same session as PROGRESS.md. Genuinely no room → record it as debt explicitly, never let it drift silently.
→
6.3 · COMMIT + PUSH
Descriptive commit, onto main
Say what changed and why (never "update"); no repo-surface identifiers. Tag the phase (phase-<N>, annotated). Push to origin/main.
→
6.4 · SET STATE
Update PROGRESS.md for next time
Status, next steps, decisions log — so the next session starts oriented. Update MEMORY.md pointers if the working agreement moved.
→
6.5 · END IT
Close the session — don't leave it open
A finished phase's context is pure cost from here. End at the phase boundary (T12) and open a fresh session for the next pick — including for the question "should I start a fresh session?". Stop the two app servers (sentinel.run api :8000, llama-server :8080), leave the Docker stack up, and never kill work in flight — inventory command lines, not process names, before stopping anything.
Guardrail — the cold-resume trap (MEASURED 2026-08-06). The prompt cache lives one hour. Re-entering a long session after a longer gap re-writes its entire accumulated context from scratch, at 2× the base input rate — and the price is set by the context carried, not the question asked. Measured on this project: a session that hit the usage limit at ~203k resident context was re-entered 3h14m later for one short question; the four messages that followed wrote 374,296 cache tokens — 28% of that whole session's cache-write volume, and ~12% of a 5-hour window. It was paid twice, because the answer was followed by tool calls instead of stopping. The same question in a fresh session costs the ~36k static prefix: ~10× less. So: a session that hits the limit is over — never resume it (largest context you will ever carry, met by a guaranteed-expired cache); ask status questions in a new session; and if a re-entry is truly unavoidable, ask and stop — take zero tool actions. The corollary for step 6.4: the handover must be written before the limit, not repaired after it, because after it you cannot run this routine at all.
Guardrail — the session-branch trap. Work committed only to a throwaway claude/<slug> branch is invisible to every future session. Before the session ends, get committed work onto main itself and pushed — a push of the session branch alone does not satisfy this.
Guardrail — the stale local main. A container can carry a local main sharing zero history with origin/main — an old snapshot baked into its starting state. git checkout main then silently rewrites the whole tree, and the "local edits" that appear are checkout artifacts of the wrong branch, not real changes. Run git merge-base main origin/main before merging — an empty result means local main is not the real branch. Never answer it with --allow-unrelated-histories or a force-push: rename the stale branch aside, rebuild from origin/main, then verify a file that should carry this session's real changes.
Guardrail — the ephemeral-container silent-loss trap (hit 2026-08-21, J3 build session). Remote ephemeral containers are reclaimed on inactivity or session end. A session that commits locally and pushes only to the session branch (claude/<slug>) loses all work permanently when the container is reclaimed — there is no error, no warning, just gone. The next session's sync check sees "0 0" because the commits never reached the remote. Two pushes are required before any session ends: (1) git push origin HEAD:main — gets work onto the trunk that survives container reclaim; (2) git push -u origin HEAD — keeps the session branch upstream in sync. Then verify: git rev-list --left-right --count HEAD...origin/main must read 0<TAB>0. Never declare a phase "built and pushed" until this count reads 0 0. The Stop hook (.claude/hooks/session_stop_check.sh) enforces this after every model response — if it warns, act on it before closing the session.
↺  next session re-enters at Phase 1 — fetch, read the state you just set, execute the next phase
Part C · Mobile Execution Delta — what changes when Nitish isn't at a machine
What this is. Nitish builds from several places — this desktop, and mobile/cloud sessions with no physical machine, no Docker, and no one watching the browser in real time. The six-phase flow in Part B runs identically either way; this part is the diff — what stays exactly the same, and what a mobile session must additionally do to reach the same standard of proof. Added 2026-07-24, after a session that closed the MVP2 boundary entirely from mobile.
1Sync & Orient
Unchangedgit fetch origin main first tool call, no exceptions.
Mobile deltaThis is the phase most likely to bite: several mobile/cloud sessions can push to origin/main between desktop sessions, so a stale local view is the norm to guard against, not the edge case. The fetch gate is not a formality here — it is the only thing standing between "where are we" and a confidently wrong answer.
2Scope & Gate
UnchangedToken-budget gate mechanics are identical — Nitish reports his 5-hour/weekly % from wherever he is.
Mobile deltaNone specific to device — the gate depends on Nitish answering, not on where he's sitting.
3Spec First
UnchangedSpec-before-implementation discipline is identical regardless of device.
Mobile deltaNone.
4Build & Verify
UnchangedNFR measurement discipline, idempotent live checks, MEASURED-vs-PROJECTED labelling — all identical.
Mobile deltaThe "if Nitish is away" branch (Part B, Phase 4) is the default assumption on mobile, not the exception. Postgres/Redis-only checks run natively in-container with no Docker; a check that genuinely needs Kafka/MinIO gets recorded as "built, awaiting live verify" until a networked/desktop session runs it — never routed around.
5Demo & Sign-off
UnchangedThe sign-off gate is still Nitish's alone — no self-sign-off, mobile or not.
Mobile deltaDemo evidence is captured, not watched live. A Playwright/Chromium render + full-page screenshot substitutes for Nitish's own eyes in the moment; sign-off, when it lands, is Nitish reviewing that captured evidence (or the artifact itself) after the fact rather than a live walkthrough at his shoulder.
6Close Out & Hand Off
UnchangedLand on main itself, tag at MVP/phase boundaries, update PROGRESS.md for the next session.
Mobile deltaThe session-branch trap bites harder here — concurrent mobile/cloud sessions are exactly the scenario that produced it (a G5 scoping session once stranded on its own throwaway branch while a parallel session saw none of it). And: any visual/HTML artifact touched this session must clear the render-and-screenshot check before commit — see the spotlight below. A mobile session has no "I'll just glance at it running" fallback.
Added 2026-07-24, amended 2026-08-03 — visual-artifact & demo validation, folded into Phase 5/6 above. Any AsBuilt diagram, proposal visual, or dashboard template edited this session gets rendered with the pre-installed Playwright/Chromium and screenshotted before being called done — not just diff-reviewed. Established closing the MVP2 boundary: a live render caught a text-overlap in a new DFD diagram that the diff alone didn't show. What changed on 2026-08-03 is where the image lands, not whether anyone looks. Order the checks cheapest-first — tag balance and an overflow assertion (~200 tokens) before any render — then have a subagent render, read the PNG and return a short verdict. The looking requirement is unchanged and non-negotiable; it was costing 22% of the project's total spend because a PNG in the main context is re-read on every later turn. If the main thread must read one: 900px viewport, JPEG q80, cropped, and late in the session.
