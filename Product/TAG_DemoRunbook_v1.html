What TAG offers

A festival platform that intends to own the whole trip, not just the wristband. Status is what can be shown today.

Live

Ticketing

Search, festival pages, zones, cart with itemised fees, guest checkout, scannable QR, a tickets page that survives a closed tab.

Live

Promoter onboarding

Application, approval with a required reason, suspension, reinstatement, audit trail both sides read.

Live

Event authoring

Festivals, venues, dated sessions, line-ups, zones, allocations — searchable by fans within seconds.

Live

Internal operations

35-role org chart, capability permissions, platform-wide event roster, hiring, fan research.

Backend only

No-oversell inventory

Proven against ten simultaneous buyers for five seats: exactly five succeeded, stock never went negative.

Stand-in

Payments

Labelled stub behind a real interface. Swapping in a live provider is contained; the provider is an open commercial decision.

Specced

Virtual queue

Admission gating for on-sale surges. Last core-ticketing piece with no external dependency — the next thing worth building.

Specced

Notifications

Confirmations and reminders. Blocked on choosing an email provider; today the link goes to the server log.

Roadmap

Travel & stays

Flights, transfers, accommodation alongside the ticket. Needs partner agreements first.

Roadmap

Dining & merchandise

On-site ordering and official merchandise through the same cart and account.

Roadmap

Fan engagement & rewards

Social features and rewards points that make the account worth keeping between festivals.

Roadmap

Vendor management

Local suppliers, artists and tourism boards, onboarded through the machinery promoters already use.

How it's built

Boring on purpose. Everything below is either load-bearing in the demo or recorded as a decision with a reason.

LayerChoiceWhy it's there
Front endReact 19 · Vite · TypeScriptEvery app surface; strict types, builds clean
Landing pageStatic HTML/CSSNo framework cost on the page that must load fastest
TicketsqrcodeQR drawn in the browser — no storage decision needed to render one
APINode · Express 5 · TypeScriptOne deployable, modular inside
Data accessPrisma 5Schema and migrations; pinned to 5 deliberately, not drifted to 7
ValidationZodEvery request body parsed before it reaches logic
Authbcrypt · server sessionsOne credential store, one token, invalidated server-side on sign-out
DatabasePostgreSQL 16Transactional guarantees the no-oversell rule depends on
CacheRedis 7Provisioned for the virtual queue; not in use yet, and the diagram says so
VerificationPlaywright · scripted API walksReal browser runs plus permission-refusal checks, per feature

Know before you're asked

Say these before someone finds them. Each is a recorded gap, and most wait on a decision rather than engineering time.

GapWhat actually happensWhat unblocks it
PaymentsThe payment step always succeeds — a stand-in behind a real interfaceChoosing a provider
EmailsNothing is sent; links go to the server logChoosing a provider
QueueingNo waiting room for a high-demand on-saleBuild — nothing external blocks it
“Near me”Ranks sample festivals only; real venues have no coordinatesCapture lat/lon at venue setup
Booking fee10% placeholderAn agreed fee schedule
Test dataFestivals and roles created by verification runs are still in the databaseAn agreed clean-up
HostingRuns on one machine; nothing to send afterwardsA cloud decision
Sign-offBuilt and verified, not formally approvedFrame it as “ready to review”, not “shipped”
